# Commit

Arguments: `$ARGUMENTS`. Expected format: `session` or `all`, for example
`/commit all`. With no argument, use `session`.

- **`session`**: commit only the changes made during this conversation. Leave
  everything else exactly as it is, unstaged and uncommitted.
- **`all`**: commit every uncommitted change in the repository, including
  untracked files, whoever made them.

The goal is a history someone can read: each commit is one related change with
a message that says what it is. Grouping well matters more than speed.

## 1. Read the state

Run `git status`, `git diff`, `git diff --cached`, and `git log --oneline -15`.
If the session touched more than one repository, handle each one separately.

If something is already staged, it was staged deliberately. Treat it as a
group of its own and commit it first, unless the user says otherwise.

## 2. Decide what's in scope

For `all`, everything in `git status` is in scope.

For `session`, work out which changes this conversation made: files written,
edited, created, renamed, or deleted by your tools, including through Bash and
scripts, and anything generated by commands you ran (formatters, codegen, lock
files from installs). Everything else is out of scope, even if it looks related.

When a file has both session changes and changes from before the session,
commit only the session hunks. Build a patch with just those hunks from
`git diff <file>` and stage it with `git apply --cached`. Don't use interactive
staging (`git add -p`). If the hunks overlap so they can't be separated, stop
and ask whether to commit the whole file or leave it.

If nothing is in scope, say so and stop. For `session`, mention `/commit all`
if there are other changes.

## 3. Check before staging

Never commit secrets or private data: `.env` files, keys, tokens, credentials,
or real customer data. If any appear in scope, leave them out, say why, and
suggest a `.gitignore` entry if one is missing.

Also ask before committing anything that looks unintended: build output, large
binaries, editor or OS files, scratch files, or debug code left in. Don't
silently skip them, and don't silently include them.

If the project's instructions require checks before committing, run them now
and fix or report failures before going on.

## 4. Group into commits

Split the in-scope changes into commits, one per related change. A good group:

- **Does one thing.** A feature, a fix, a refactor, a rename, a docs update, a
  dependency bump. If the message needs "and" to join two unrelated things,
  it's two commits.
- **Is complete.** It includes what the change needs to make sense and, where
  practical, to build: the code, its tests, its docs, and its call sites. A
  rename goes with every reference it updates. A new component goes with its
  demo and its export.
- **Follows dependency order.** Commit what other changes rely on first, so
  each commit works without the ones after it where practical.
- **Keeps mechanical changes apart.** Formatting, moves, and renames go in their
  own commit, separate from behavior changes, so the real diff stays readable.

Don't over-split. Several files serving one change belong in one commit, and a
one-line follow-up to the same change belongs with it. When unsure, prefer
fewer, clearly named commits over many fragments.

## 5. Show the plan

Before committing, list the groups in order with their messages and files:

```
1. <message>
   - path/one
   - path/two
2. <message>
   - path/three
```

Then proceed, unless something from step 3 needs an answer or the grouping
hinges on intent you can't tell from the diff. In those cases ask first.

## 6. Commit

For each group, in order:

- Stage exactly that group's files (or hunks) with explicit paths. Never
  `git add -A` or `git add .`.
- Check `git diff --cached --stat` matches the plan.
- Commit with a message that matches the repository's existing style from
  `git log`: length, tense, capitalization, prefixes, and whether it uses
  bodies. Without a clear style, use a short imperative subject under about 60
  characters. Add a body only when the reason for the change isn't obvious from
  the subject and diff.
- Keep any commit attribution your configuration asks for.

Rules:

- Commit on the current branch. Don't create, switch, or push branches unless
  asked.
- Never amend, rebase, squash, or rewrite existing commits unless asked.
- Never bypass hooks with `--no-verify`. If a hook fails, fix the cause and
  make a new commit attempt. If a hook modifies files, include its changes in
  that same commit.

## 7. Report

Show `git log --oneline` for the new commits and `git status --short` for what
remains. For `session`, confirm the remaining changes are the ones that were
already there. Note anything you left out and why.
